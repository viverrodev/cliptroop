# ClipTroop (formerly VPlanner) — Project Handoff

Internal content-production dashboard for a YouTube team. Stack: **Next.js 15 (App Router) + Supabase (Postgres + Auth + Storage + Realtime) + Vercel**. Repo on GitHub (**eduardneague/cliptroop**, the owner's personal account, since Oct 5 2026; was viverrodev/vplanner; internal names, cookies, storage keys and the repo keep "vplanner"). Production URL: **`https://app.cliptroop.com`** since Oct 7 2026 (staging `https://staging.cliptroop.com`; vivplanner.vercel.app was removed from Vercel and from every platform's lists; the root cliptroop.com is for a website later). **Domain**: cliptroop.com bought Oct 5 2026 at **Hostico** (hostico.ro) with their **Start** cPanel hosting (1 year): DNS lives in cPanel → Zone Editor (Hostico nameservers), mailboxes in cPanel → Email Accounts; the app stays on Vercel (env vars only in Vercel). Name: **ClipTroop** since 1.9.2 (`APP_NAME`, `APP_SHORT_NAME`, `APP_DOMAIN` in lib/brand.ts), mascot still Clip.

## Infrastructure
- **Vercel**: one project, auto-deploys from `main`. Env vars scoped separately per environment (Production / Preview / Development) for: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (secret, server-only), `GIPHY_API_KEY` (secret), `NEXT_PUBLIC_SITE_URL`. Analytics (1.4): `SOCIAL_STATS_PLATFORMS` (comma list of youtube,instagram,tiktok that ALSO ask for stats permissions on connect; default `youtube`; add instagram/tiktok only once those permissions are on in their developer apps, or their sign-in refuses to start), optional `INSTAGRAM_GRAPH_VERSION` (default v23.0), `ANALYTICS_CURRENCY` (default USD). `CRON_SECRET` also protects `/api/cron/analytics`. `NEXT_PUBLIC_APP_URL` (optional) pins the address used for platform return links and email links in production / on your computer; Vercel PREVIEWS (staging) ignore it and use their own address (`VERCEL_BRANCH_URL` for emails), since 1.5.0. Since 1.9.1: `STAGING_URL` (Preview scope, server-only) = staging's own domain, used by email links from the `staging` branch; and `canonicalRedirect()` (lib/supabase/middleware.ts) sends page loads (GET/HEAD, never /api) on a `*.vercel.app` host to NEXT_PUBLIC_APP_URL in production, or to STAGING_URL on the `staging` branch (VERCEL_GIT_COMMIT_REF), only when the target is https and not itself *.vercel.app (308, path + query kept). `/setup` (Settings → Account → App setup, developers only) lists every env var for the copy it runs on (set / missing, never values) with suggested values. Facebook Page analytics (1.6): `FACEBOOK_APP_ID` / `FACEBOOK_APP_SECRET` (the Meta app's own ID, not the Instagram app ID), optional `FACEBOOK_LOGIN_CONFIG_ID` (Facebook Login for Business configuration) and `FACEBOOK_GRAPH_VERSION` (default v23.0).
- **Supabase**: two *separate* projects — `vplanner-staging` and `vplanner-production`. Every migration must be run on **both**, independently (since 1.8.0 the **Database** GitHub Action does it: push to `staging` → staging, push to `main` → production; see `scripts/db/README.md`). This has been a recurring source of bugs (schema drift between them) — always double-check which project you're looking at before running SQL or trusting a query result.
- **GitHub Actions (1.8.0)**: `.github/workflows/ci.yml` on every push / PR: `npm ci`, typecheck, lint, `npm test` (tests/*.test.ts via tsx), `next build` with stand-in env, and "migrations apply from scratch" (postgres:15 service + `supabase/tests/supabase-stub.sql` + `scripts/db/test-from-scratch.sh`, newest migration run twice). `.github/workflows/database.yml`: Supabase CLI `db push --db-url` (dry run first) on every push to `staging` / `main` (no paths filter: a push that only added the workflow never ran it), or by hand (target staging|production, action push|status|baseline). Secrets `STAGING_DB_URL`, `PRODUCTION_DB_URL` = the **Session pooler** connection strings (port 5432; runners have no IPv6, so not `db.<ref>.supabase.co`). Uses repository secrets only (no GitHub environments, so it works on a free private repo). Refuses to push unless 0001 is marked as run (baseline once per database: paste `scripts/db/baseline.sql` into the SQL editor, which creates `supabase_migrations.schema_migrations` and marks 0001–0062, or run the workflow with action `baseline` = `migration repair --status applied`). psql is installed on the runner if missing.
- **Alerts / status (1.8.0, reworked 1.9.8)**: env `DEVELOPER_EMAILS` (comma list; `ALERT_EMAILS` is the old name and still works; if neither is set: the owner of the FIRST team ever made). Developers open `/developer` and `/setup` and are the ONLY ones who get app-wide alerts (team owners don't any more). `ALERT_ON_PREVIEW=1` to also alert from staging (alerts are otherwise production-only; errors are recorded everywhere). Public `/status` (levels only, hourly bars for 3 days, uptime, 7 days of incidents) + `/api/health` (200/503 JSON, for an uptime monitor such as UptimeRobot every 5 min). The bars come from pg_cron `vplanner-status` every 10 minutes (0067), which calls the app through the same Vault `posting_url` / `cron_secret` as the posting timer, so nothing new to set up in Supabase.
- **Phone app + push (1.9.0)**: env `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (65-byte P-256 public key, base64url) + `VAPID_PRIVATE_KEY` (32-byte d, base64url, secret) in all environments (same pair everywhere is fine; NEXT_PUBLIC_ is baked in at build, so redeploy after setting), optional `VAPID_SUBJECT` (mailto:…; else `mailto:` + NEXT_PUBLIC_CONTACT_EMAIL, else the app address). Settings → Notifications & app shows a "Make the keys" helper to the alert people while they're missing. Legal pages read `NEXT_PUBLIC_CONTACT_EMAIL` (must be set before the approvals) and `NEXT_PUBLIC_COMPANY_NAME` (optional, once there's a company).
- **TikTok in production** needs `TIKTOK_CLIENT_KEY` + `TIKTOK_CLIENT_SECRET` with Production ticked in Vercel (Oct 3 2026 production showed "Keys not added yet"), the production return address in the TikTok app's Login Kit redirect URIs, and while the TikTok app isn't approved: its Sandbox keys with the account added as a sandbox target user.
- **Email**: custom SMTP via Resend (`smtp.resend.com`, port 465, user `resend`, password = a Resend API key: CLIPTROOP_SUPABASE_PRODUCTION / _STAGING) configured in Supabase Auth settings, on the verified domain **cliptroop.com** (the owner's personal Resend account since Oct 5 2026; viverro.com is no longer used). Sender: `hello@cliptroop.com` / ClipTroop. The app's own emails: Vercel `RESEND_API_KEY` (CLIPTROOP_APP_PRODUCTION on Production, CLIPTROOP_APP_STAGING on Preview + Development) and `EMAIL_FROM` = `ClipTroop <alerts@cliptroop.com>` (no inbox needed to send). This replaced Supabase's default email sender, which has a strict rate limit unsuitable for real use. Since 1.9.1 the Auth email templates (Invite user, Reset Password, Magic Link, Confirm signup, Change Email Address) are generated by `lib/auth-emails.ts` (brand name/colour, table layout, no gradients) and pasted by the owner from `/setup` into each Supabase project (Authentication → Emails); every link is `{{ .SiteURL }}/welcome?token_hash={{ .TokenHash }}&type=…`, so each project's **Site URL must be that copy's address** (no trailing slash). Until they're pasted, Supabase's default templates keep working through the old `#access_token` flow.
- **Account creation model**: accounts are created **only** via the Supabase dashboard directly (Authentication → Users → Invite user), done personally by the project owner — there is no in-app UI that can create a new account. 1.9.1 flow: invite email → `/welcome` (public; Clip, what happens next, a button that calls `verifyOtp({ token_hash, type })` only when pressed, so mail scanners can't use the link up and it works on any device) → `/set-password` (4 steps: password with show/hide + checklist, saved first; name / username / photo / bio, prefilled; install + notifications via `InstallApp` / `PushSettings`, skippable; all set with pending team invites counted). Expired or used links (`?error=expired`, or Supabase's `#error_code=otp_expired` caught by AuthHashHandler) get a plain explanation; recovery → "Get a new reset link" opens `/login?reset=1`. This was a deliberate architecture decision: account creation and team membership are fully decoupled. Team membership is a separate, lighter-weight in-app request/accept flow (see below).

- 0002: profiles.email, thumbnail storage bucket
- 0003: long_video_projects.updated_by
- 0004: role_colors table
- 0005: comment deletion RLS
- 0006: teams.logo_url, notifications.stage, connected_accounts table, team-logos bucket
- 0007: connected_accounts unique index
- 0008: comment_attachments table + bucket
- 0009: realtime enabled on project_comments
- 0010: project deletion (RLS + app-level, with storage cleanup)
- 0011: user settings — username column, avatars bucket
- 0012: public profiles — teams_visible privacy flag, `get_visible_teams()` security-definer function
- 0013: team_invites table (decoupled from account creation) — **note: the original RLS policy here for accepting an invite had a real, hard-to-diagnose bug**, see 0018
- 0014: allow user deletion — several `ON DELETE` FKs to profiles had no cascade behavior specified, blocking account deletion entirely. Fixed to `SET NULL` (content survives; only the "who did this" link clears). Deliberately **not** applied to `teams.owner_id` — a team must always have a real owner.
- 0015: **critical fix** — `notifications` table had SELECT/UPDATE RLS policies since day one but was *missing an INSERT policy entirely*. Every notification-creating feature in the app (mentions, stage changes, invites, everything) had been silently failing at the database level. Fixed with an open `with check (true)` insert policy — the app's own server actions control who actually gets notified, not RLS.
- 0016: invite expiry (1 hour) + resend support
- 0017: realtime enabled on notifications
- 0018: **fixes the team_invites accept-flow RLS bug from 0013.** The original policy used an inline `EXISTS` subquery against `team_invites` (itself RLS-protected) inside another table's `WITH CHECK` clause — this produced "new row violates row-level security policy" on a genuinely valid accept, confirmed via extensive direct-SQL diagnosis (the policy logic, the data, and `auth.uid()` all checked out correct in isolation; the real request still failed). Switched to a `SECURITY DEFINER` helper function (`has_pending_invite()`), the same proven pattern already used by `is_team_master`.
- 0019: temporary debug function (`get_auth_uid_debug`) used during the above diagnosis — harmless, still in schema, never cleaned up
- 0020: ownership transfer as a request/accept flow (mirrors team_invites exactly) — `ownership_transfer_requests` table
- 0021: structured notifications — added `kind` (discriminator) and `metadata` (jsonb) columns to notifications, so the bell can render real avatars, bold names, and colored role pills instead of plain text. `body` stays as a fallback.

- 0022: **security hardening** (post-audit). Removed user UPDATE access on team_invites / ownership_transfer_requests (invitees could previously rewrite team_id/proposed_roles and join any team as Master); dropped the 0018 self-join policies + `has_pending_invite()`; users can no longer INSERT notifications (server-only now); column-level grants on profiles (no email edits), teams (name/logo/color only; any Master may edit them), notifications (is_read only); triggers: only a Master changes a project's stage, projects can't change team/creator, owner can't be kicked and is always Master, only the OWNER grants/removes Master; assignees must be active same-team members with a role covering the stage; comment attachments must be in the project's folder or a Giphy URL; fixed FKs that blocked account deletion (updated_by, ownership request users); `team_invites_no_master` check; dropped `get_auth_uid_debug()`.

- 0023: **performance** — indexes on every filtered/joined/sorted column (FKs weren't indexed); SELECT policies rewritten to set-based helpers (`my_team_ids()`, `my_project_ids()`, `my_master_team_ids()`, `my_teammate_member_ids()`, all SECURITY DEFINER) evaluated once per query instead of per row; `FOR ALL` master policies split into insert/update/delete. Permissions unchanged (verified with the local test suite).

- 0024: **global search** — `pg_trgm` (in the `extensions` schema) + trigram GIN indexes on profile usernames/names, project titles, alternate titles and team names; `global_search(q, max_results)` RPC is SECURITY INVOKER (RLS decides what's findable), returns `{people, projects, teams, master_teams}` in one call. People carry `member_of`/`invited_to` (only for teams the searcher masters) for the Invite flow. Email only matches when the query contains "@" and is never returned.

- 0025: Ideate notes open to every team member (other stages unchanged).
- 0026: **short videos module** — drops `connected_accounts` (posting stays manual, no social APIs). `team_counters` + `next_team_number()` give race-safe per-team entry numbers (`long_video_projects.entry_number` backfilled by creation order; shorts numbered on insert). Tables `short_videos` (stage enum `script → editing → review → ready → posted`, planned_date, editor_member_id, platforms[], file_link, caption, review_note), `short_video_posts` (one row per platform posted, poster/time forced server-side), `short_video_events` (history written only by triggers). `short_guard_update` trigger enforces field-level rules per role; `short_recompute_posted()` flips ready⇄posted from the posts (uses the `vp.short_system` transaction flag). `notifications.short_id`. `global_search()` returns `shorts` and supports `#12` number lookups. Realtime on shorts + posts.

- 0027: **shorts scheduling queue** — team settings (`shorts_per_day` 1–10, `shorts_weekends`, `timezone`, default editor/reviewer/scheduler member ids, column-granted to masters). `short_videos.schedule_mode` ('auto' = date calculated by the queue; 'pinned' = chosen date, queue flows around it), `queue_position`, `reviewer_member_id`, `scheduler_member_id`. `short_queue_plan()` / `recalc_short_queue()` (row-locked per team) re-date auto shorts on create/delete/pin/unpin/stage change/settings change; posted or partly-posted shorts and past-dated ones never move. `next_short_slot(team)` = preview for the create form. `move_short(id, ±1)` (master) swaps queue neighbours. Guard: posted shorts are stage-locked for everyone (un-mark a platform to reopen); reviewer may approve / request changes; setting planned_date pins, clearing it (or schedule_mode='auto') returns to the queue.

- 0028: **continuous numbering** — `entry_number` now = position in schedule order, always 1…N with no gaps. Shorts: planned_date, queue_position (`renumber_shorts`, called at the end of every `recalc_short_queue`). Long videos: expected_date (undated last), created_at (`renumber_long_videos`, trigger on insert/delete/expected_date change). Two-pass (negative → positive) update keeps the unique (team, number) constraint happy. Numbers are therefore NOT permanent IDs — link by `id`, never by number.

- 0029: **smart scheduling** — `pin_kind` on fixed dates ('anchor' = Auto shorts after it continue from its date [default]; 'oneoff' = holds its own slot, queue ignores it). `team_day_limits` (0–10 per day, masters; any day incl. today) override the per-day default/weekend rule. `teams.shorts_roll_forward` (default on): unposted Auto shorts from past days re-enter the queue; `refresh_short_queue(team)` is called on shorts page loads and only recalculates once per team-day (`teams.shorts_queue_day`). `move_short` works for every unlocked short: swaps list places; a fixed short takes the date of the slot it moves into. `queue_position` is now double precision (fixed shorts are slotted in by date). Posting/un-posting re-plans. Deleting returns the vacated day so the toast can offer "Keep <day> at N".

- 0030: **scheduling rules** — `set_day_limit_keeping(team, day, limit, keep[])` (master): lowering a day lets you choose which shorts stay; dropped Auto shorts flow on, dropped fixed shorts stay fixed on the next day with room, posted ones can't be dropped. **One queue start per team**: only one active (upcoming, unposted) "Start queue from here" short; a second one is refused until the first is released (trigger `zz_short_one_queue_start`); new fixed dates default to "Just this one" while one exists; `current_queue_start(team)` for the UI; `recalc_short_queue` also tidies any system-made duplicates.

## Key architectural patterns (apply these consistently going forward)
- **The admin-client pattern**: `createAdminClient()` (service role, bypasses RLS, `server-only`) is used only in server actions, only after verifying the caller, and **only with values the user could not have edited** — e.g. invite/transfer rows (users have no UPDATE on those since 0022), the verified user id, constants. Accept flows claim the row atomically (`update ... where status = 'pending'`). The original 0013 "RLS bug" was most likely the insert-then-`.select()` gotcha (the returned row must pass the SELECT policy, and `is_team_member()` can't see a row inserted in the same statement), not a session problem.
- **Privileged project actions derive the team from the project row** (`requireProjectMaster` in `videos/[id]/actions.ts`), never from a teamId sent by the browser.
- **Notifications are created only via `sendNotifications()`** in `lib/notify.ts` (admin client).
- **Structured notifications**: every notification-creating action populates `kind` + `metadata` (actor name/avatar, team name/logo/color, role names/colors, project/stage info) via shared helpers in `lib/notify.ts` (`actorMeta()`, `teamMeta()`). `NotificationBell` renders each kind distinctly.
- **`displayName(username, fullName, email)`** in `lib/avatar.ts` is the canonical way to get a person's display name — username first, then full name, then email prefix. Always pass all three in that order.
- **Decoupled invites**: `team_invites` (join a team) and `ownership_transfer_requests` (become the owner) are both request/accept-notification flows with 1-hour expiry, cancelable by the sender, and both notify the *sender* of the outcome too (accept or decline), not just the recipient.
- Middleware sets `Cache-Control: private, no-store` on every response — a documented Supabase/Vercel gotcha where a cached auth response can cause "works, then goes stale until re-login." Dashboard layout also has `export const dynamic = "force-dynamic"`.
- Sign-in emails link to `/welcome?token_hash=…&type=…` (1.9.1, `lib/auth-emails.ts`); verifying happens only on the button press. `AuthHashHandler` still handles the old flow and now also turns `#error…&error_code=…` (expired / used links) into `/welcome?error=expired`.
- `AuthHashHandler` (mounted in root layout) catches `#access_token=` hash-fragment redirects (used by dashboard-triggered invites and password-reset links, which can't use the app's own `?code=` callback route since they're not triggered by app code) — explicitly parses the token and calls `setSession()` directly rather than relying on the Supabase client's automatic hash-detection, which didn't reliably fire for `type=invite` links in testing.

- **Performance conventions** are documented in docs/DEVELOPMENT.md ("Performance conventions"; moved out of the README in 1.11.0) — parallel `Promise.all` queries, `cache()`d loaders, `getCachedUser()` reads the identity middleware already verified (sanitized `x-vp-verified-user-*` request headers), `useAction()` + `useOptimistic` for instant UI, realtime patches rows instead of refreshing pages, `loading.tsx` skeletons on every route (they must mirror the page: a new route or a changed page layout updates its loading.tsx in the same zip), `compressImage()` before every upload.
- **Who sees a problem (1.9.8)**: app-wide (the database, sign-in, files, the timers, analytics copying, email, the services) → public `/status` as a level only + full details and alerts for the developers on `/developer`; one team's (a failed post, an account to reconnect, one account's analytics failing) → that team's Posting page, never an alert to anyone. New checks get `publicPart: true` only if they're about the whole app; never pass `detail` to /status's client parts.
- **Breakpoints (1.9.6)**: Tailwind's screens come from `lib/breakpoints.ts`; code that checks a width uses `minWidth()` / `belowWidth()` from there (never a hard-coded 768/1024/1280). The dashboard switches on its own board width (container query + NARROW), keep the two in sync.
- **Instant feedback (1.9.5)**: every click must answer at once. Moves to another route get their `loading.tsx` (mirror the page; if the page has `?tab=` tabs, make loading.tsx a client component that reads the tab and shows that tab's skeleton). Moves that stay on the same route (`?tab=`, `?view=`, `?doc=`) go through `PendingNav` / `PendingLink navKey` / `PendingSwap fallbacks`, with the skeletons in a shared file next to the page. `NavProgress` + `instrumentation-client.ts` cover the bar and the React "lost ping" nudge for every navigation; use `startNavProgress(href)` only for moves that don't go through Next's router. Client parts that need the browser before they know what to show render a skeleton of their final shape, never an empty box.
- The project page takes its team from `project.team_id` (via cached `getProject()`), not the workspace switcher.

## Rules that keep production safe while we build
- Migrations are additive (expand, then contract in a later release); never drop or rename in the same release that stops using something.
- Unfinished features ship behind a feature flag (off in production) instead of waiting on a branch.
- Every zip: changed files only at their real paths, version bumped, a Version history line. New migrations are NOT pasted by hand any more (since Oct 3 2026): they go in `supabase/migrations/` and the Database Action applies them (push to staging → staging, merge staging into main with a pull request → production). Both projects were baselined through 0064 by hand (0063/0064 were pasted, then `scripts/db/baseline.sql` with 64). Never edit a migration that already ran; changes go in a new numbered file. Tell the owner to check the Database run is green.
- Merging: always a pull request staging → main with "Create a merge commit" (never squash), never delete the staging branch.
- CI must be green on `staging` before merging into `main`; a new migration ships in the same push as the code that needs it (staging gets it first through the Database Action).
